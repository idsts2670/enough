## Risks / gaps to escalate before Phase 3 implementation

1. **Plaid suggested-category surface.** Grep for `plaid.*category | imported_category | category_id` in `loot-core/src/server/accounts` returned no matches. Either Plaid-suggested categories are not persisted today, or they're stored under a name I didn't find. **Action:** before Phase 3 starts, open a 30-minute investigation pass to confirm (a) whether Plaid import stores a suggested category, (b) where, (c) whether it's surfaced to the user. If not stored, the "transactions to review" workflow needs a different definition (e.g., uncategorized only, with rule-based suggestions instead of Plaid suggestions).

2. **Recurring detection.** Schedules are user-created. Copilot's "Recurrings" surface includes auto-detected recurring charges (Netflix, Spotify, etc.) — that detection is non-trivial (matching merchant + amount + cadence). PLAN.md explicitly defers this. Phase 3 "Recurrings — Next 14 Days" card therefore renders **user-created schedules only**, with a clear empty-state when no schedules exist. Don't overpromise auto-detection in UI copy.

3. **Account type field.** Verify that every account in `loot-core` has a `type` field with consistent values (`checking`, `savings`, `credit-card`, `investment`, `loan`, `other`). If types are free-form or null for legacy accounts, the "grouped by type" rendering needs a fallback bucket.

4. **Monthly Spending derived value.** The card needs a single number like _"Spent $X this month, $Y under budget."_ `spending-spreadsheet.ts` returns time-series; need a thin wrapper to derive the headline figure. Trivial, but list it as Phase 3 implementation work.

## Summary

**Of the 6 Phase 3 dashboard cards:**

- **4 cards** have existing selectors and need no new query work (Net Worth, Top Categories with light filter logic, Recurrings via schedules, Accounts summary).
- **1 card** needs a thin derived wrapper (Monthly Spending headline number on top of existing time-series).
- **1 card** needs a new query (Transactions to Review) AND a clarification on Plaid suggested categories (see risk #1).

**Net assessment:** Phase 3 is **not blocked on backend work**. The selectors are ~85% in place. Risk #1 (Plaid suggested-category surface) is the only thing that could expand scope; resolve before Phase 3 starts.

## Appendix A: Plaid Suggested Category Investigation

Added by Codex during Phase 0 startup.

Status: **Risk #1 is resolved for the current worktree.**

Findings:

- Plaid suggested category is present in the sync pipeline as `plaidSuggestedCategory`.
- `packages/loot-core/src/server/accounts/sync.ts` calls `getOrCreatePlaidSuggestedCategory(...)` during normalization and assigns the returned category id to `trans.category` when no explicit category is already present.
- The raw Plaid transaction is stored in `raw_synced_data`, including `plaidSuggestedCategory`, so the suggestion can be backfilled later.
- `backfillPlaidSuggestedCategories(...)` reads `raw_synced_data?.plaidSuggestedCategory` for uncategorized Plaid transactions and assigns a matching category.
- Existing tests in `packages/loot-core/src/server/accounts/sync.test.ts` cover creating Plaid categories, assigning them during account sync, and backfilling uncategorized transactions from raw sync data.

Implication for Phase 3:

- The "Transactions to Review" card does **not** need a backend investigation blocker for Plaid category persistence.
- It still needs product semantics: distinguish transactions that are uncategorized from transactions auto-categorized from Plaid and not yet user-reviewed.
- If the review state is not already stored, Phase 3 should add a lightweight reviewed/unreviewed marker rather than re-solving Plaid category persistence.
